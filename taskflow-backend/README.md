# TaskFlow Backend — Task 01, 02, 03, 04 & 05

This repo implements the full TaskFlow assignment: **Task 01** (Data
Modeling & Database), **Task 02** (Authentication & Authorization),
**Task 03** (REST API for Projects & Tasks), **Task 04** (Background Jobs
& Email Notifications), and **Task 05** (Testing & API Documentation).

Everything below was actually run against a live PostgreSQL + Redis stack
while building this — including a real retry/backoff/dead-letter-queue
cycle, timed and verified — not just written from memory.

## Tech stack

| Category | Choice | Why |
|---|---|---|
| Language | Node.js + TypeScript, Express 5 | Required |
| Database | PostgreSQL 16 | Required |
| ORM | **Drizzle ORM** (not Prisma) | Prisma's engine binaries are fetched from `binaries.prisma.sh` at install/generate time, which isn't reachable in every environment. Drizzle is 100% TypeScript with no native binary download, generates plain SQL migrations, and is explicitly allowed by the assignment ("Prisma, TypeORM, Drizzle, ..."). |
| Job queue | Redis + BullMQ | Required |
| Containers | Docker Compose | Required — API + Worker + Postgres + Redis |

## Architecture

```
src/
  config/env.ts            # all env vars read in one place, fails fast if missing
  db/
    schema.ts               # Drizzle schema = source of truth for the data model
    client.ts                # pg Pool + Drizzle instance
    migrate.ts                # runs drizzle/migrations/*.sql against DATABASE_URL
    seed.ts                    # seed data per assignment spec
  lib/
    redis.ts                  # shared ioredis client (used by rate limiter + BullMQ)
    queue.ts                    # BullMQ queues + enqueueAssignmentEmail() helper
  jobs/
    email.types.ts             # job payload shape
    email.worker.ts             # BullMQ Worker: mock send, retry/backoff, DLQ on exhaustion
  worker.ts                    # worker process entrypoint (separate from server.ts)
  middleware/
    auth.middleware.ts        # verifies JWT access token -> req.user
    org.middleware.ts          # verifies org membership (DB lookup) -> req.org
    rateLimiter.middleware.ts   # Redis-backed 10 req/min/IP limiter for /auth/*
    error.middleware.ts          # turns AppError/ZodError into the standard JSON shape
  utils/pagination.ts          # pure offset-pagination helper
  modules/
    auth/                      # register/login/refresh/logout/logout-all
    organizations/               # member listing + RBAC-gated member management
    projects/                     # project CRUD + dashboard
    tasks/                          # task CRUD, filters, assign/unassign, bulk, FTS
    jobs/                             # GET /jobs/:id
  app.ts                        # express app assembly
  server.ts                      # API entrypoint (loads dotenv, starts app.listen)
drizzle/
  migrations/
    0000_init.sql                # generated by `drizzle-kit generate` from schema.ts
    0001_fulltext_search.sql      # hand-written: tsvector trigger + GIN index (bonus)
```

**Route → Controller → Service → Data** separation, unchanged since
Task 02: controllers only parse (Zod) and shape responses; all query/
business logic lives in `*.service.ts`, the only layer that imports `db`
(or, for tasks, `queue.ts`). Every service function takes `orgId` as an
explicit parameter sourced from `req.org.id`, never from the request body.

## Data model (Task 01)

See `src/db/schema.ts` — every table, FK, and index has an inline comment
explaining the decision. Summary of the FK/CASCADE reasoning:

- `org_members`, `refresh_tokens` → CASCADE on their parent user/org (pure
  join/session rows, meaningless once the parent is gone).
- `projects.org_id`, `tasks.project_id`, `task_assignments.*`,
  `comments.task_id` → CASCADE (child rows have no independent meaning).
- `tasks.org_id` → RESTRICT. This is a **denormalized** column (org is
  derivable via `project.org_id`) kept directly on `tasks` so that
  tenant-scoping/authorization queries don't need a join on every request.
  RESTRICT is a safety net against ever hard-deleting an org while tasks
  still reference it.
- `comments.author_id` → RESTRICT (comments are an audit trail; we don't
  want user deletion to silently rewrite or anonymize history).

Indexes are justified per-column in `schema.ts` (org-scoping columns,
status/priority/due_date for the required task filters, a composite
`(project_id, deleted_at)` for the dominant query shape, and a GIN index
over a trigger-maintained `tsvector` for full-text search).

**Bonus implemented:** soft delete (`deleted_at` on `projects`/`tasks`) and
PostgreSQL full-text search on `tasks.title`/`tasks.description`
(`0001_fulltext_search.sql` — trigger keeps `search_vector` in sync, GIN
index makes `search_vector @@ websearch_to_tsquery(...)` fast).

Migrations are real, ordered SQL files under `drizzle/migrations/`, applied
with `npm run db:migrate` — there is no hand-maintained `schema.sql`.

## Auth & RBAC (Task 02)

- `POST /auth/register` — creates a **user** and a **new organization** in
  one transaction, with that user as `org_admin` of it. (Design choice:
  registering is "create your workspace"; existing admins add teammates via
  `POST /orgs/:orgId/members`.)
- `POST /auth/login`
- `POST /auth/refresh` — rotates the refresh token on every use. If a
  **revoked** token is presented (reuse of an already-rotated token — a
  signal of possible theft), every active session for that user is revoked
  as a precaution.
- `POST /auth/logout` — revokes the specific refresh token.
- `POST /auth/logout-all` *(bonus)* — revokes every refresh token for the
  authenticated user.
- `GET /auth/me` — sanity-check endpoint for a token.

All four required endpoints are rate-limited to **10 requests/minute/IP**
via a Redis-backed limiter (`rate-limiter-flexible`), so it's correct even
across multiple API replicas.

**Passwords:** bcrypt, cost factor 12 (`config.bcryptCostFactor` enforces a
floor of 12 even if `BCRYPT_COST_FACTOR` is misconfigured lower).

**Tokens:** JWT access tokens (15 min TTL) are stateless. Refresh tokens
(7 day TTL) are persisted in `refresh_tokens`, but **only as a SHA-256 hash**
— a database leak alone can't be replayed as a session. Each refresh JWT
carries a `jti` claim equal to its DB row id, so refresh/logout are O(1)
primary-key lookups, not a hash-scan.

**RBAC / multi-tenancy:**
- `authenticate` middleware verifies the JWT and loads the user — it does
  **not** attach org context, because a user can belong to multiple orgs.
- `requireOrgMembership(paramName)` takes the org id from the **route
  param** (e.g. `/orgs/:orgId/members`), looks up an `org_members` row for
  `(req.user.id, orgId)` in the DB, and only then attaches `req.org = {id,
  role}`. If no membership row exists, it returns **403** without
  revealing whether the org itself exists — this is what "cross-tenant
  access must return 403 and not leak data" means in practice, and it's
  the same mechanism that enforces "don't trust client-provided org_id":
  the id from the URL is just a lookup key, never trusted at face value.
  Verified against a live server (see below) with a second, unrelated org.
- `requireOrgAdmin` gates a route to `role === "org_admin"` and must run
  after `requireOrgMembership`. Demonstrated on
  `POST/PATCH/DELETE /orgs/:orgId/members*` (add/remove members, change
  roles). The equivalent gate for "admins can delete projects" will be
  applied to the project-delete route in Task 03.
- Every service function takes `orgId` as an explicit parameter sourced
  from `req.org.id`, never from `req.body` — see
  `organizations.service.ts` for the pattern that Task 03's project/task
  services will follow.

### Smoke-tested manually (see commit history / dev notes)

Registered two independent orgs, then confirmed:
- Login + `/auth/me` round-trip with a real JWT
- Refresh token rotation, and that reusing a rotated token is rejected (401)
- Logout revokes the token; a subsequent refresh with it fails (401)
- Org A's admin can list/add members; a member from unrelated Org B gets a
  clean **403** when addressing Org A's `orgId` directly
- A `member`-role user gets **403** on the admin-only add-member route but
  **200** on the read-only list-members route
- Validation errors return the required `{error, code, details}` shape
  with per-field issues
- Duplicate email registration returns `409 EMAIL_ALREADY_REGISTERED`
- 11th+ request to `/auth/*` within a minute from the same IP returns `429`
- `password_hash` values in the seeded DB are `$2b$12$...` (bcrypt, cost 12)

## Setup

### Option A — Docker Compose (recommended)

```bash
cp .env.example .env
# edit JWT_ACCESS_SECRET / JWT_REFRESH_SECRET to long random values
docker compose up --build
```

The API container runs migrations automatically on boot
(`node dist/src/db/migrate.js && node dist/src/server.js`), then listens on
`http://localhost:3000`. The `worker` service (Task 04's BullMQ consumer)
starts alongside it automatically. Seed manually if you want sample data:

```bash
docker compose exec api node dist/src/db/seed.js
```

Interactive API docs: `http://localhost:3000/docs`.

### Option B — Local (no Docker)

Requires a local PostgreSQL 16 and Redis 7.

```bash
cp .env.example .env   # point DATABASE_URL at your local Postgres
npm install --legacy-peer-deps
npm run db:migrate
npm run db:seed        # optional: 2 orgs, 5 users, 13 tasks, assignments, comments
npm run dev             # API on http://localhost:3000, docs at /docs
npm run worker:dev       # in a second terminal - consumes the email-notification queue
```

`--legacy-peer-deps` is needed because `ts-jest`'s peer range hasn't caught
up to the TypeScript version some other devDependency pulls in; it's a
devDependency-only resolution quirk, not a runtime issue.

### Running the tests

```bash
npm test              # 9 files, 61 tests, real Postgres + Redis (see TASK-05-NOTES.md)
npm run test:coverage # same, + HTML/lcov report in coverage/
```

Needs the same local Postgres/Redis as above; the suite creates and
migrates its own `taskflow_test` database automatically.

## API reference (Tasks 01–04 surface)

Full interactive reference: `http://localhost:3000/docs` (Swagger UI) or
import `docs/TaskFlow.postman_collection.json`. This section covers the
auth endpoints inline; see `TASK-03-04-NOTES.md` for projects/tasks/jobs.

All error responses share this shape:
```json
{ "error": "Human readable message", "code": "MACHINE_CODE", "details": {} }
```

### `POST /auth/register`
```json
// request
{ "email": "a@b.com", "password": "min8chars", "name": "Ada", "organizationName": "Ada Inc" }
// 201 response
{ "user": {...}, "organization": {...}, "accessToken": "...", "refreshToken": "..." }
```

### `POST /auth/login`
```json
{ "email": "a@b.com", "password": "min8chars" }
// 200 -> same shape as register
```

### `POST /auth/refresh`
```json
{ "refreshToken": "..." }
// 200 -> { "accessToken": "...", "refreshToken": "..." }  (old refresh token is now revoked)
```

### `POST /auth/logout`
```json
{ "refreshToken": "..." }
// 204 No Content
```

### `POST /auth/logout-all` *(bonus)*
Requires `Authorization: Bearer <accessToken>`. Revokes all sessions. `204`.

### `GET /auth/me`
Requires `Authorization: Bearer <accessToken>`. Returns the current user.

### `GET /orgs/:orgId/members`
Any member of `:orgId` can list members: `{ "data": [{userId, email, name, role, joinedAt}] }`.

### `POST /orgs/:orgId/members` *(org_admin only)*
```json
{ "email": "existing-user@x.com", "role": "member" }
```

### `PATCH /orgs/:orgId/members/:userId/role` *(org_admin only)*
```json
{ "role": "org_admin" }
```

### `DELETE /orgs/:orgId/members/:userId` *(org_admin only)*
`204 No Content`.
